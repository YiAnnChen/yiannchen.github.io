固定旗標 FTEC 協定的組合式正確性證明

對象是一個固定的協定：Steane [[7,1,3]] 碼、t=1、預算 r+s≤1、每個穩定子一條旗標量測電路、現有的終止規則，以及 288 項的旗標 decoder 表。我們用 CPAchecker 把「兩次觀測相同的執行不會造成邏輯錯誤」拆成 181 個單次執行的殘餘驗證與 4 條引理，再由組合器把證據接成完整的證明。

CPAchecker 無法在瀏覽器裡執行，所以本站展示它存下來的證據；另外把協定的模擬程式 scalar.c（也就是 CPAchecker 證明的對象）編譯成 WebAssembly，讓你在瀏覽器裡把每一種可能的故障都實際跑一次。

驗證什麼the claim

協定在一個 Pauli frame 模型中執行：資料位元 q0…q6，症狀輔助位元 q7，旗標位元 q8。每次執行結束後，我們記下 decoder 看得到的完整觀測 m = (n, b, h₀,…,h₇)：輪數 n、分支 b（一般或旗標），以及每輪 12 位元的症狀與旗標紀錄。

定理（本模型內）
對任意兩個合法執行 f₁, f₂，若完整觀測相同，則 σ(E₁ E₂) = 0  ⟹  E₁ E₂ ∈ S   （忽略全域相位） 其中 Eᵢ 是第 i 次執行結束時、修正前的資料 Pauli 錯誤，σ 是理想症狀，S 是穩定子群。Pauli 以 (x, z) 遮罩表示，乘法就是 XOR。

直觀地說：decoder 只看得到觀測，所以兩個觀測相同的執行一定會套用同一個修正。只要它們的錯誤差異不是一個「症狀為零卻不在 S 裡」的邏輯算子，這個共同修正就不會把其中一個執行修成邏輯錯誤。

這不是直接的雙執行模型檢查。把協定展開兩次的 pair 模型，CPAchecker 沒有得到結論。這裡的 TRUE 來自組合式證明：先分別證明 181 份「單次執行」的結果和 4 條數學引理，再由組合檢查程式 compose.js（負責逐筆核對所有證據，確認它們能接成完整定理）把它們接起來。

合法配置（t=1）

無錯誤；一個重量一的初始資料錯誤（r=1, s=0，7 位元 × 3 種 = 21）；或乾淨基線前三輪內的一個電路故障（r=0, s=1，3 輪 × 6 穩定子 × 94 = 1,692）。

不在模型內

idle 故障、古典控制故障、修正操作本身的故障，以及 t>1、r+s>1、其他碼或其他 decoder。

協定the fixed protocol

Steane 碼有 6 個穩定子，但它們只用到 3 組「4 個資料位元」：同一組位元上全放 Z，就是 Z 型穩定子；全放 X，就是 X 型穩定子。

位元組合Z 型穩定子X 型穩定子
q3、q4、q5、q6Z1 = Z₃Z₄Z₅Z₆X1 = X₃X₄X₅X₆
q1、q2、q5、q6Z2 = Z₁Z₂Z₅Z₆X2 = X₁X₂X₅X₆
q0、q2、q4、q6Z3 = Z₀Z₂Z₄Z₆X3 = X₀X₂X₄X₆

這三組位元來自 Hamming [7,4] 碼的檢查矩陣，這正是 Steane 碼的構造方式。

每一輪依序量測 Z1、Z2、Z3，再量測 X1、X2、X3。每個穩定子用一條量測電路，每條電路有 10 個操作：

操作內容可注入的故障
op0, op1準備症狀位元 q7、旗標位元 q8準備翻轉（1 種）
op2…op76 個 CNOT：4 個連到資料位元，第 2、5 個（op3、op6）連到旗標CNOT 後任意非恆等兩位元 Pauli（15 種）
op8, op9量測 q7、q8量測翻轉（1 種）

六個穩定子共用同一套排程（資料、旗標、資料、資料、旗標、資料），差別只在接到哪 4 個資料位元（見上表），X 型再把 CNOT 的控制與目標對調。圖中只有實線的資料位元會被這個穩定子碰到。

旗標是做什麼的

量測電路裡的 CNOT 會把症狀位元 q7 和資料位元連在一起。若故障發生在電路中間，同一個錯誤可能經由後面的 CNOT 擴散到兩個資料位元上。一般的 Hamming 解碼假設最多只有一個位元出錯，遇到這種「被擴散的錯誤」可能修錯。旗標位元 q8 就是用來偵測這種情況：只要中間出了這類故障，旗標就會量到 1。

終止規則：兩種停法

一般分支旗標分支
什麼時候走所有旗標都是 0某一輪有任何旗標量到 1
何時停止連續三輪量到相同的症狀旗標亮起後，再完整量兩輪就停
代表什麼錯誤最多影響一個資料位元可能有一個擴散到兩個位元的錯誤
怎麼決定修正只看最後一輪的症狀看整段量測紀錄，查表決定

旗標亮起後為什麼還要再量兩輪？因為 t=1 只允許一個故障，而它已經發生了，之後的量測都是乾淨的，能量到資料錯誤真正的症狀。

最多量 8 輪。程式用 check(n<8u) 把「超過 8 輪」當成錯誤回報，不會偷偷略過那些情況。

Decoder：怎麼決定修正

一般分支：拿最後一輪的 6 位元症狀，對照穩定子表找出是哪一個位元出錯，修正那一個位元（Hamming 解碼）。

旗標分支：查一張「量測紀錄 → 修正」的對照表。這裡的完整量測紀錄是指從第一輪到停止為止、每一輪 12 個位元的量測結果：6 個穩定子的症狀，加上 6 個旗標。例如「第 1 輪 Z1 的旗標亮起，共量 3 輪，每一輪 X1 的症狀都是 1」就是一筆紀錄。這張表是用 Python 寫的參考模擬程式，把所有會讓旗標亮起的單一故障逐一模擬，記下每一種會出現的量測紀錄和對應的正確修正，共 288 筆。

旗標分支為什麼一定要看整段紀錄、不能只看最後一輪？因為不同位置的故障，最後一輪可能量到完全一樣的結果，只有從「哪一輪、哪個穩定子的旗標亮了」才分得出來。Playground 的對照 B 就是只看最後一輪，會找到 2,880 對分不出來的例子。

程式把兩種分支包成同一個函式 correction()，它只看量測紀錄，看不到實際的錯誤：

unsigned correction(unsigned n,unsigned b,unsigned h0,...,unsigned h7) {
 unsigned last;
 if(b) return flaglookup(n,h0,h1,h2,h3,h4,h5,h6,h7);
 last=n==1u?h0:n==2u?h1:n==3u?h2:n==4u?h3:n==5u?h4:n==6u?h5:n==7u?h6:h7;
 return decode(last&63u); }

找不到表項時回傳哨兵 0x80000000u，run() 以 check(cor!=0x80000000u) 把它當成錯誤。

證明鏈proof chain

每一步都是一個（或一組）CPAchecker 驗證工作，全部使用 config/bmc.properties、迴圈界限 128、位元向量編碼。

每一步下面列出負責檢查它的小程式（.c 檔，點開可看原始碼）。TRUE 代表 CPAchecker 證明它成立；標「對照」的是刻意寫錯的版本，應該得到 FALSE，用來確認檢查真的會抓到錯。

  1. 每個合法執行都滿足殘餘界限

    把 1,714 種輸入分成 181 個互斥區（initial 區 22 種，加上每個「輪 R、穩定子 K、操作 O」一區）。每區驗證真正的 run()，證明 wt_min(C·E) ≤ s、r+s ≤ 1，並且 ec == correction(觀測)。組合器獨立重算輸入域，確認覆蓋完整且互斥。
    residual/*.c（181 份，每區一份驗證程式）· manifest.json（分區清單與每份程式的指紋）· results/residual/*（每區的 CPAchecker 執行紀錄）

  2. 預算放寬

    由 rᵢ+sᵢ ≤ 1 得 sᵢ ≤ 1，所以 wt_min(C·Eᵢ) ≤ 1。
    budget_relaxation.c（檢查這一步）· TRUE

  3. 單一殘餘的症狀與奇偶關係

    若 wt_min(A) ≤ 1，則 parity(aₓ) = [σₓ(A) ≠ 0]，Z 部分同理。
    residual_signature.c（檢查這一步）· TRUE

  4. 同觀測 → 同修正（機器檢查）

    181 區每一區都證明 ec == correction(en,eb,eh0..eh7)；小程式 common_correction.c 再證明在中間把所有全域輸出改成任意值後，correction() 的結果不變。所以 M(f₁)=M(f₂) 蘊含 C₁=C₂。
    common_correction.c（檢查這一步）· TRUE；對照 common_correction_broken.c（故意讓修正偷看實際錯誤）· FALSE

  5. 消去共同修正，推出 pair 條件

    令 Aᵢ = C·Eᵢ，則 A₁ ⊕ A₂ = E₁ ⊕ E₂ = D。若 σ(D)=0，則兩個殘餘的症狀相同，由步驟 3 它們的奇偶也相同，所以 D 的 X、Z 奇偶皆為偶，即 D ∈ S。
    signature_pair.c（檢查這一步）· TRUE；對照 pair_bridge_broken.c（故意拿掉第二次執行的前提）· FALSE

步驟 3、5 的奇偶引理只對 Steane（CSS 碼）與 t=1 成立。一般碼距論證 wt(P₁P₂) ≤ s₁+s₂ < d 沒有經過機器檢查。完整推導見證明說明文件（逐步推導，以及每一步對應到哪段程式）。

對照組的作用

每條關鍵引理都配一個刻意弄壞的版本，預期 FALSE。它們確認檢查真的能抓到錯誤，不是因為前提恆假而「空洞地」成立。

殘餘界限失敗時

若某個 decoder 讓步驟 1 失敗，結論是組合式證明不適用，不是「協定錯誤」。pair 條件可能仍然成立，兩者必須分開回報。Playground 的對照 A 示範這種情況。

這些紀錄都經過自動核對：每一次都用同一組 CPAchecker 設定（BMC、迴圈上限 128、精確的 32 位元整數運算、保留「迴圈上限不夠就不能回報 TRUE」的檢查），而且 CPAchecker 實際分析的程式內容和紀錄裡的指紋相符。原始資料：evidence.json（本節表格用的全部紀錄）、COMPOSITION.json（組合檢查的最終報告）、manifest.json（181 區的分區清單與每份程式的指紋）。

TRUE 在這裡的意思

BMC 搭配 bounding assertions：若迴圈界限 128 不足以涵蓋所有路徑，結果會是 UNKNOWN，不會是 TRUE。

位元精確

bitprecise_wrap（TRUE）與 _bad（FALSE）確認 unsigned 溢位是以 32 位元位元向量精確建模。

為什麼不在瀏覽器跑 CPAchecker

CPAchecker 是 Java 程式並依賴原生 SMT 求解器。瀏覽器端改由 WASM 窮舉同一個有限模型，作為獨立的交叉檢查。

原始檔

scalar.c協定的模擬程式：電路、故障、終止規則與 decoder 都在這裡，也是被證明的對象 residual/r1_k0_op2.c一區的驗證程式範例：第 1 輪、穩定子 Z1、第一個 CNOT 後發生故障 residual/initial.c「無故障或只有初始錯誤」那一區的驗證程式（22 種情況） legacy.c另一份獨立寫成的同一協定模擬程式，寫法完全不同，Playground 用它交叉比對 ftec_wasm.cPlayground 的檢查程式：把上面兩份模擬程式包起來，逐一測試所有情況 證明說明文件定理的嚴格敘述、逐步推導，以及每一步對應到哪段程式

WASM 與證據用的是同一份模型

Playground 會先下載模擬程式 scalar.c，在瀏覽器裡算出它的指紋（SHA-256），確認和 CPAchecker 證明時用的那份完全相同，再執行由它編譯出的 WebAssembly。

範圍與限制scope

  1. t=1 寫死在模型、residual()（只列舉重量一）與輸入域（1,714 種）裡。residual() 開頭的 check(s<=1u) 會擋下越界呼叫。
  2. 旗標 decoder 是 Python 窮舉產生的 288 項表；驗證過程不列舉控制流，但建模流程本身用了列舉。
  3. 步驟 3、5 的奇偶引理只對 Steane、t=1 成立；一般碼距論證沒有機器檢查。
  4. 物理模型（閘的錯誤傳遞、量測基底、旗標電路）只做過三份同源實作（Python、legacy C、scalar C）的差異測試，還沒有用 Stim 之類獨立的穩定子模擬器核對。
  5. 直接展開兩次協定的 pair 分析，CPAchecker 沒有得到結論。
  6. 若 decoder 讓殘餘界限不成立，組合式證明就不適用；這不代表 pair 條件不成立。

重現reproduce

需要 Java 21、CPAchecker 4.2.2 與 Node。在專案的驗證資料夾中依序執行：

node partitions.js                       # 產生 181 區的驗證程式與分區清單，並確認沒有遺漏或重疊
node run_partitions.js --resume --seconds 60   # 逐區執行 CPAchecker
node run_lemmas.js                       # 執行 4 條引理與 5 個對照組
node compose.js                          # 核對全部證據，寫出最終報告 COMPOSITION.json
node test_compose.js                     # 故意破壞證據，確認組合檢查會拒絕

本站的 WASM 由 YoWASP 的 Clang（編譯成 WebAssembly 的 LLVM）建置，不需要原生編譯器：

npm i @yowasp/clang
node tools/build_wasm.mjs      # 把模擬程式編譯成 Playground 用的 ftec.wasm
node tools/test_wasm.mjs       # 在 Node 中跑一次 Playground 的全部檢查
